# Constraints

Discovered facts about the outside world. **Not** choices — see `DECISIONS.md` for those.
These expire: anything older than 90 days gets re-verified.
Dead ends that burned two or more attempts also belong here.

|---|---|

| 2026-08-17 | **Stooq is unusable** — sits behind a JavaScript bot-check that returns an HTML challenge page, not CSV. |
| 2026-08-17 | **Yahoo `quoteSummary` + `v7/quote` return 401 "Invalid Crumb"** from a server. No keyless forward P/E, PEG, consensus, targets, margins, short interest or institutional holdings. |
| 2026-08-17 | **Yahoo `v8/finance/chart` works keyless** from Supabase. Daily and `range=max` (quarterly candles, real highs/lows, back to first trade — 1984 MU, 1980 INTC). |
| 2026-09-05 | **Yahoo hourly gives 2 years**, ~3,500 bars per ticker, `dataGranularity: "1h"`. An earlier note claiming a 3-month cap was wrong. |
| 2026-08-17 | **SEC XBRL works keyless** (`data.sec.gov`), stamped with filing dates. Needs a descriptive User-Agent with contact email. Published rate limit: 10 requests/second. |
| 2026-09-05 | **`^VIX3M` is free and live** on the chart endpoint — term structure costs nothing extra. |
| 2026-09-05 | **Yahoo's `range=max` series and the daily series agree on basis** (both split/dividend adjusted). MU all-time high = $1,255.00 from both. Safe to mix. |
| 2026-09-05 | **Warm-up floors.** Seed influence drops below 0.01% after: RMA(14) 125 bars, EMA(21) 97, EMA(50) 231, EMA(200) 922. Below these, suppress the value. |
| 2026-09-05 | **SNDK has only 82 weekly bars** (spun off from WDC 2025-02-13) — its weekly 21 EMA is seed-sensitive until roughly March 2027. |
| 2026-09-12 | **GitHub Free does not support protected branches on private repos** — public repos only, or any repo on Pro. Drove the decision to go public. |
| 2026-09-12 | **The prototype Supabase project sits in a Vercel-managed org**, where member invites flow through Vercel rather than Supabase team settings. The real project should live in a self-owned Supabase org. |
| 2026-09-12 | **Never run git inside the Cowork device VM — not even `git status`.** That shell cannot delete files, so any git command that touches the index leaves `.git/index.lock` behind and GitHub Desktop then refuses every operation. `git status` looks read-only but refreshes the index and creates the lock. Verified twice, the second time by walking into it after documenting it. Use `find`/`ls`/`cat` to inspect the working tree; use GitHub Desktop or a native terminal for anything git. |
| 2026-09-12 | **Supabase's GitHub integration ships with "Deploy to production" OFF.** Linking the repo at project creation does nothing on its own; the toggle lives at Project Settings → Integrations → GitHub, with the production branch name (`main`) and working directory (`.`). Enabling it does **not** replay earlier merges — only the next push to `main` deploys. The first migration PR (#1) merged with the toggle off and applied nothing; verified via `list_migrations` = empty, `pg_tables` = empty. Preview branches per PR are Pro-only; production deploys work on Free. |
| 2026-09-12 | **jsr.io is blocked from the coding sandbox; the npm registry is not.** `deno test` on a `jsr:` import fails with 403 at the proxy. Edge functions therefore use `npm:` / `node:` specifiers (decision 0017) so the same code that deploys is the code that was tested. `*.supabase.co` is also unreachable from the sandbox, so a function is invoked from inside the project — `net.http_post` in SQL — never with curl from here. |
| 2026-09-12 | **Deno 2 picks `node_modules` mode if any parent directory has a `package.json`** and then refuses `npm:` specifiers it has not installed. A clean checkout has none, so CI is fine; locally, run tests from a directory with no `package.json` above it, or pass `--config` with `"nodeModulesDir": "auto"`. Cost two attempts. |
| 2026-09-13 | **The Supabase GitHub integration deploys `supabase/functions/` on merge to `main`, on the Free plan.** `ingest` appeared as version 1 within ~60 s of the ingest PR (issue #5) merging, `verify_jwt` read from `supabase/config.toml`. Same mechanism as migrations (decision 0016); no GitHub Action needed. |
| 2026-09-13 | **Claude's SQL access to the project runs as `supabase_read_only_user`.** It can read every table, `net._http_response` and `vault.secrets` (names only), but cannot decrypt Vault, cannot queue `net.http_post`, and cannot write. So a manual ingest is always triggered by a human in the dashboard SQL editor (runs as `postgres`), and Claude reads the outcome. This is the right shape, not a limitation to work around. |
| 2026-09-13 | **The edge runtime's `SUPABASE_SERVICE_ROLE_KEY` is not byte-identical to the legacy `service_role` key on the dashboard's API Keys page.** Verified by elimination: Vault held a genuine `role: service_role` JWT (219 chars, no whitespace) and a byte-compare still 401'd (INCIDENTS.md). Exact cause unverified — nothing in the repo can read that env var. Consequence: never gate on a byte match with it alone; decode the gateway-verified JWT's role claim instead (`auth.ts`). |
| 2026-09-13 | **A table created by a migration grants `service_role` nothing useful.** Migrations run as `postgres`; Supabase's permissive default privileges belong to `supabase_admin`; default privileges are per owner role. Result on every table we create: `service_role=Dxtm/postgres` — truncate, references, trigger, maintain, and no SELECT/INSERT/UPDATE/DELETE. Every migration must grant explicitly (decision 0018). Read the truth with `select relname, relacl from pg_class` — `information_schema.role_table_grants` shows only what the *querying* role can see, which from a read-only session looks like "no grants at all" and misleads. |
| 2026-09-13 | **`range=max&interval=1d` does NOT return daily bars.** Yahoo picks a granularity from the span and ignores `interval`. Measured on the first live backfill: ^GSPC 169 bars 90.8 days apart (quarterly) from 1984-12-01, ^NDX 165 at 91.2, ^SOX 389 at 30.4 (monthly) from 1994-06-01, ^VIX 441 at 30.4 from 1990-02-01. Bars land on the 1st of the month or quarter, which are often not trading days, so they do not collide with real daily rows and must be deleted rather than overwritten. Use explicit `period1`/`period2` epochs for full daily history. Hourly `range=2y&interval=1h` is unaffected — verified exact at 3,484 bars. |
| 2026-09-13 | **Yahoo rate-limits Supabase's egress IP, and the penalty outlasts the burst.** ~90 requests in 6.9 s (4 concurrent, 250 ms pauses) all succeeded, then every later request returned plain-text `429 Too Many Requests` — three concurrent probes 3 minutes later, and a single probe 6 minutes later. Not JSON, so it must be caught before parsing. Ingest now runs 2 concurrent with 1 s pauses and abandons the run on a 429. Cooldown length not yet measured. |
| 2026-09-13 | **`query1.finance.yahoo.com` is disallowed by robots.txt for WebFetch**, so the sandbox cannot probe Yahoo even through the sanctioned tool, and routing around it (curl, a browser on the user's machine) is off limits. Every Yahoo experiment runs from Supabase via `net.http_get`, fired by a human in the SQL editor, and Claude reads `net._http_response`. |
