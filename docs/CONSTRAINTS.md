| 2026-09-13 | **Claude's SQL access to the project runs as `supabase_read_only_user`.** It can read every table, `net._http_response` and `vault.secrets` (names only), but cannot decrypt Vault, cannot queue `net.http_post`, and cannot write. | 2026-09-13 | **The edge runtime's `SUPABASE_SERVICE_ROLE_KEY` is not byte-identical to the legacy `service_role` key on the dashboard's API Keys page.** Verified by elimination: Vault held a genuine `role: service_role` JWT (219 chars, no whitespace) and a byte-compare still 401'd (INCIDENTS.md). Exact cause unverified — nothing in the repo can read that env var. Consequence: never gate on a byte match with it alone; decode the gateway-verified JWT's role claim instead (`auth.ts`). |
| 2026-09-13 | **A table created by a migration grants `service_role` nothing useful.** Migrations run as `postgres`; Supabase's permissive default privileges belong to `supabase_admin`; default privileges are per owner role. Result on every table we create: `service_role=Dxtm/postgres` — truncate, references, trigger, maintain, and no SELECT/INSERT/UPDATE/DELETE. Every migration must grant explicitly (decision 0018). Read the truth with `select relname, relacl from pg_class` — `information_schema.role_table_grants` shows only what the *querying* role can see, which from a read-only session looks like "no grants at all" and misleads. |
| 2026-09-13 | ~~Yahoo-specific; kept because the LESSON generalises: a provider may silently return a different granularity than you asked for, so assert bar spacing after any backfill.~~ **`range=max&interval=1d` does NOT return daily bars.** Yahoo picks a granularity from the span and ignores `interval`. Measured on the first live backfill: ^GSPC 169 bars 90.8 days apart (quarterly) from 1984-12-01, ^NDX 165 at 91.2, ^SOX 389 at 30.4 (monthly) from 1994-06-01, ^VIX 441 at 30.4 from 1990-02-01. Bars land on the 1st of the month or quarter, which are often not trading days, so they do not collide with real daily rows and must be deleted rather than overwritten. Use explicit `period1`/`period2` epochs for full daily history. Hourly `range=2y&interval=1h` is unaffected — verified exact at 3,484 bars. |

Not JSON, so it must be caught before parsing. Ingest now runs 2 concurrent with 1 s pauses and abandons the run on a 429. Cooldown length not yet measured. |
